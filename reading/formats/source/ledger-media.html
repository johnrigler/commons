Ledger media: content, presentation and format names

27 November 2026 · Author identity: LcudkPQzLuuqsnzHSmJ7iLREaHStvPKRVb · Unsigned, AI-assisted technical field notes. CC0.

A ledger record can contain an image, a catalog of links, and instructions for how an application should display them. A useful reader separates those roles. Chisel names recognized shapes, shows a compact format tag, and opens structured content in a colored, collapsible JSON tree. The original fields remain available as formatted source and as a JSON download.

Each format deserves its own entry: the identifying marker and field layout, an actual transaction and output, the application or specification when established, an authoring example, and the reader's current limits. These entries document interpretations without changing the stored transaction.

BSV section feed — BSV_SECTION_1

This is the reader's name for an observed JSON layout, not a claim that it became an industry standard. The supplied Chisel export of BSV transaction 7f137c54…198665, output 0 contains an object with p: "BSV_SECTION_1", section deepdive, a numeric timestamp, and 37 media entries under f. The current reader recognizes the marker together with an array-valued f.

FieldObserved role
pDeclared layout identifier, BSV_SECTION_1.
sSection label. Other sections can use the same layout.
tNumeric timestamp; the sample is consistent with milliseconds since the Unix epoch. It is a payload claim.
fArray of media-catalog entries.
Fields inside each entrytxid, title, channelName, owner, category, duration, section, ts, tags, isLinked, platform, embedId, externalUrl, thumbnailUrl.

The embedded labels and links identify claimed platforms and channels. They do not establish which application or person originally wrote the catalog, whether an owner controlled a key, or whether linked media remain available. Some item txid values are platform identifiers rather than 64-digit transaction hashes. No independently verified publisher specification is established for this layout in this note.

Writing compatible source

The following is a synthetic example of the observed shape. Keep the exact declared identifier, an array for f, JSON numbers and booleans in their native types, and UTF-8 text. Preserve unknown fields when editing an existing record. This example describes intentional legacy JSON authoring; it introduces no new Chisel publishing envelope.

{
  "p": "BSV_SECTION_1",
  "s": "example",
  "t": 1700000000000,
  "f": [{
    "txid": "youtube_example",
    "title": "Example media item",
    "channelName": "example",
    "platform": "youtube",
    "isLinked": true,
    "externalUrl": "https://example.org/watch",
    "thumbnailUrl": "https://example.org/thumbnail.png",
    "tags": ["example"]
  }]
}

A compatible reader must also know the original transaction carrier. A JSON object alone does not specify a locking script, fee, signing procedure, or complete transaction. Chisel currently inspects this structure and its original output; this guide does not add a section-feed writer.

JSON media and presentation records

For an unfamiliar layout, start with what the bytes establish: a JSON object or array, its field names, and any explicit p, protocol, schema or format identifier. Chisel labels image-related fields plus style-related fields as an Image & presentation record. That is a descriptive category, not an attribution to a particular publisher.

The JSON viewer uses indentation and separate colors for keys, strings, numbers, booleans and null. Each object and array opens independently. Large arrays show 100 children at a time; long strings open separately. Formatted source and the JSON download preserve access to every value. The format tag filters the currently loaded catalog; it does not scan the entire blockchain.

To reproduce an established application format, retain its exact identifier, field names, types, encoding, media references and version rules. Establish required fields from its own specification or multiple complete examples before presenting a guessed recipe as compatible. Base64 inside JSON, a binary image push and an outbound image URL are different storage choices with different byte costs and dependencies.

The image-with-faded-edges example has not been identified from a transaction source in this investigation. Its specific application, effect semantics and authoring rules remain unassigned. A later entry should cite that transaction and output before naming its original format.

Presentation instructions belong with the artifact

HTML and CSS can describe layout, opacity, masks and edge fading. Their presence is meaningful source material; printing their syntax in the main feed makes the record difficult to read. Chisel puts detected presentation source in its own collapsed source entry. It does not apply carried styles to the portal or run carried scripts.

Reproducing an original effect requires its actual declaration, image reference, dimensions, color or transparency model, and any application-specific interpretation. A style field might contain CSS or an application-defined preset. Treating every such field as ordinary browser CSS would invent behavior. Once its rules are established, a dedicated bounded renderer can interpret supported properties and identify the rest as source.

Bitcom B: a typed file carrier

The original B specification by unwriter defines a carrier for file data. Its protocol address is 19HxigV4QyBv3tHpQVcUEQyq1pzZVdoAut. Following the OP_RETURN marker, use separate Script data pushes for the address, file bytes, media type, encoding and optional filename, in that order. A MIME type describes content; it does not name the application that published it.

Protocol push: 19HxigV4QyBv3tHpQVcUEQyq1pzZVdoAut
Data push:     exact file bytes
Media push:    image/png
Encoding push: binary
Filename push: example.png

For an intentional HTML file, use UTF-8 source bytes, text/html, UTF-8 and the chosen filename. These are separate push fields, not a space-joined text string. B can carry binary images directly; Base64 is not required. Actual network policy, input selection and signing are separate transaction-building concerns. B itself does not authenticate an author's identity.
