Recording calls with Shizuku and ShizuCallRecorder

The setup steps, the hoops, and the test that determines whether it works on your phone.

What each piece does

ShizuCallRecorder is the recorder. Shizuku starts a service with ADB shell privileges on an unrooted phone and makes supported elevated operations available to authorized apps. It is not root. F-Droid supplies an installation route for the recorder; it does not remove Android’s permission restrictions.

Android documents that capturing voice-call uplink and downlink requires CAPTURE_AUDIO_OUTPUT, a permission unavailable to ordinary third-party apps. Microphone permission alone does not provide both sides of a call. This is why installing a recorder may lead through Developer options, debugging access and a helper service. Android audio-source documentation.

Scope and test status

This walkthrough arose from a Samsung Galaxy A15 5G, model SM-A156U, reported as running Android 16. Pairing timed out and a startup attempt displayed “certificate unknown.” Successful two-sided recording on that handset has not been confirmed. The guide documents the setup path, not a completed compatibility test.

Check the recorder’s documentation for your installed version. The upstream README reviewed for this article lists Android 12 or later as its main requirement, limited Android 11 support, and Android 16 support in its test table. Older repository descriptions may still say Android 11+. Newer upstream releases include VoIP support with version-dependent limits; do not assume the F-Droid build has those features or that every calling app works.

Basic wireless setup

  1. Install ShizuCallRecorder from its F-Droid listing. Install the separate Shizuku helper from a download linked by the official project. Record which release and publisher you installed. Current recorder documentation also recommends a Shizuku fork; instructions for fork-specific automation are not interchangeable with the original helper.
  2. On Samsung, open Settings → About phone → Software information. Tap Build number seven times and enter the device PIN if asked. Return to Settings → Developer options.
  3. Following the Shizuku manual, enable USB debugging, then Wireless debugging. Connect the phone to Wi-Fi. Android 11 and later support this on-device startup path without attaching a computer.
  4. In Shizuku, tap Pairing and permit notifications. In Android’s Wireless debugging screen, select Pair device with pairing code. Keep that dialog open, pull down the notification shade, and enter the displayed six-digit code in Shizuku’s notification. The ordinary IP address and port display is not the pairing code.
  5. Wait for pairing success, then return to Shizuku and select Start. Confirm its main screen reports that the service is running. A Starter log window by itself is not confirmation.
  6. Open ShizuCallRecorder and authorize its Shizuku request. Complete its own permissions and recording settings. Decide whether to record manually or automatically; opening the app alone does not establish either behavior.
  7. Make a short, agreed test call to a regular phone number. Play back the saved file and confirm both voices, intelligibility, duration and the beginning and end. Repeat for Bluetooth, speakerphone or Wi-Fi calling if you intend to use those routes. Retest after updates and reboots.

Where it fails

  • Pairing timeout: start pairing again and generate a fresh code. Allow Shizuku to run in the background and keep the pairing dialog open. Check Wi-Fi and notification access.
  • Certificate error: the startup failed; the message alone does not establish its cause. Check whether pairing actually succeeded. If a stale Shizuku pairing is listed, forget that entry and pair again. The official manual also suggests toggling Wireless debugging when startup fails.
  • After reboot: the original unrooted Shizuku startup must be performed again. Pairing normally persists; starting the service and pairing are different operations.
  • Stops unexpectedly: manufacturer background restrictions can interfere. Consult the helper’s device guidance and the recorder’s logs. A “running” status still does not prove that audio was captured.
  • Missing opening seconds: newer recorder/helper combinations offer managed startup. Upstream documents a possible 1–20+ second startup delay. These controls depend on helper version or fork; do not expect them in every installation.
  • Silent or one-sided file: this configuration has failed the test. Hidden Android APIs, OEM changes, audio routing and application versions can break capture. Do not rely on it for an important call until playback succeeds.

Access has a cost

Authorize only apps you intend to give Shizuku access. Debugging and elevated shell operations expand what authorized software can do; this is more access than a normal microphone permission. Avoid exposing an unauthenticated legacy ADB TCP listener as a shortcut. Follow the documentation for the installed helper rather than enabling every option described by a different fork.

Retain a record you control

For an institutional call, a local recording lets you revisit exact wording without depending on the institution to supply its copy. This technical guide does not determine recording or publication permission. The recorder does not obtain other participants’ consent for you; resolve the applicable requirements before using automatic recording or sharing a call.

First establish the recorder’s actual export location. Do not assume Termux can read an app-private directory or a Storage Access Framework URI as a filesystem path. Export a test file to a shared folder, grant Termux appropriate storage access, and verify that it can read the bytes. Termux:API alone does not grant access to every app’s files.

The proposed Mogwai workflow is: preserve the original file privately; calculate its SHA-256; record the call date, timezone, app version and test results in Daisy; make a separate redacted listening copy; record each redaction interval and hash that derivative separately. A hash detects byte changes; it does not prove who spoke or that the recording is complete. Public Commons instructions can describe the method while the original recording and identifying information remain private. See the call-recording artifact model.
